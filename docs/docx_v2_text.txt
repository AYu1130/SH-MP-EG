摘 要
智能家居场景中，不同品牌终端设备采用迥异的无线协议，用户需多个专用网关分别管理，形成“协议孤岛”；云端集中式架构在响应延迟与断网场景下亦难以满足即时控制需求。本文以边缘计算思想为指导，设计并实现一款支持多协议接入的边缘智能网关。
研究基于树莓派与ESP32硬件平台，构建了支持Wi-Fi、BLE、MQTT协议的软件系统，实现协议适配、统一消息路由及本地联动规则引擎，采用四层分层架构将数据处理与决策下沉至边缘侧。
实测结果表明，Wi-Fi传输时延均值45.2ms，BLE时延均值78.6ms，跨节点联动响应时延均值136.2ms，均满足设计目标；断网场景消息补传成功率100%，系统在7×24小时长时运行中保持稳定。该方案为消费级物联网边缘计算的落地提供了可复现的低成本参考。
关键词：智能家居，边缘智能网关，多协议互联，协议转换，MQTT
ABSTRACT
In smart home scenarios, terminal devices from different manufacturers adopt disparate wireless protocols, compelling users to manage multiple dedicated gateways separately—a predicament known as the “protocol silo” problem. Meanwhile, cloud-centric architectures struggle to meet real-time control demands under latency constraints and network interruption conditions. Guided by edge computing principles, this paper designs and implements a multi-protocol edge intelligent gateway.
Based on Raspberry Pi and ESP32 hardware platforms, this research constructs a software system supporting Wi-Fi, BLE, and MQTT protocols, implementing protocol adaptation, unified message routing, and a local event-driven rule engine. A four-layer hierarchical architecture is adopted to offload data processing and decision-making to the edge side.
Experimental results demonstrate that the average Wi-Fi transmission latency is 45.2 ms, BLE latency averages 78.6 ms, and cross-node event-driven response latency averages 136.2 ms, all meeting the design targets. The message retransmission success rate reaches 100% under network disconnection scenarios, and the system remains stable during 7×24-hour long-run testing. This solution offers a reproducible, low-cost reference for deploying edge computing in consumer-grade IoT.
Keywords: Smart Home, Edge Intelligent Gateway, Multi-protocol Interco-nnection, Protocol Conversion, MQTT

第1章 绪论
1.1 研究背景与意义
1.1.1 研究背景
物联网技术与人工智能、5G通信的深度融合正在推动智能家居领域从单品智能向全屋智能加速演进。在这一转型过程中，一个结构性的矛盾逐步显现：不同厂商的终端设备各自采用Wi‑Fi、低功耗蓝牙（BLE）、Zigbee、Z‑Wave等互不兼容的无线通信协议，用户在同一居住空间内被迫部署多个专用网关，形成了严重的“协议孤岛”现象。碎片化的协议生态不仅抬高了普通消费者的部署门槛，更导致跨品牌设备间的协同控制变得极为困难。
从系统架构的角度审视，当前主流智能家居方案大多沿用“终端—云端—终端”的通信范式。传感器数据与控制指令须经由远端服务器中转，一旦家庭宽带发生波动或中断，整个系统随之瘫痪。即便在网络正常条件下，公网往返时延也通常维持在数百毫秒的量级，对于照明即时响应、安防实时告警等时延敏感型场景而言，这样的响应速度难以令人满意。
将部分计算与决策能力从云端下沉至家庭网络的边缘侧，是化解上述困境的一条值得探索的技术路径。处于边缘位置的智能网关能够在本地完成多协议设备的接入适配、数据融合与联动规则执行，在断网条件下依旧维系核心功能的运转，同时将关键操作的响应时延压缩到用户可接受的范围之内。本文正是沿着这一思路，尝试设计并实现一款面向智能家居场景的多协议边缘智能网关。
1.1.2 研究意义
从理论层面分析，现有边缘计算网关的研究讨论多集中于工业物联网与城市级部署场景，面向消费级智能家居场景的轻量级边缘网关系统性设计方法尚未形成足够的学术积累。本研究尝试对这一缺口做出补充，为多协议数据模型的统一化表述、边缘侧联动规则引擎的轻量化设计以及端—边—云协同策略的优化提供具有一定参考价值的设计思路与实验依据。
在工程实践层面，本研究形成了一套基于树莓派4B主控、ESP32‑S3与STM32F103协同接入的软硬件参考方案，整体硬件成本可控且具备良好的性价比。网关侧实现了协议转换与本地联动规则引擎，实测条件下本地控制响应时间可控制在500毫秒以内，MQTT端到端传输延迟不超过200毫秒；在网络中断场景中，系统依靠本地规则引擎依旧能够维持联动功能的正常运行。该方案可为嵌入式开发人员及智能家居系统集成商提供一套具体、可复现的设计参考。
1.2 国内外研究概况
1.2.1 国内研究现状
国内学者围绕智能家居网关的多协议融合问题同样开展了广泛探索。杨飞宇 REF _Ref230017597 \r \h \* MERGEFORMAT [1]以面向智能家居的边缘智能网关为研究对象，设计了“感知层—边缘层—网络层—应用层”四层架构，并提出了融合模糊理论与层次分析法的二级数据融合算法，在降低数据冗余的同时兼顾了融合精度。吴磊和朱杰 REF _Ref230017695 \r \h \* MERGEFORMAT [2]从协议层面切入，设计了一种适用于家庭多协议网关的通用通信协议，通过在协议数据单元中定义设备编号、协议类型和命令类型等字段，达成对Wi‑Fi、蓝牙、Zigbee等设备的统一管控。刘廷 REF _Ref230017723 \r \h \* MERGEFORMAT [3]梳理了有线与无线通信技术在物联网智能家居中的融合应用路径。
葛悦涛和尹晓桐 REF _Ref230017746 \r \h \* MERGEFORMAT [4]对边缘计算的发展趋势进行了系统性综述，归纳了从云计算向边缘计算迁移的技术动因与关键挑战；王哲 REF _Ref230017779 \r \h \* MERGEFORMAT [5]分析了边缘计算的产业落地现状与未来演进方向；杨帆 REF _Ref230017802 \r \h \* MERGEFORMAT [6]探讨了移动物联网技术在智慧家居中的系统设计方法与应用实践。在网关原型实现方面，刘亮亮等人 REF _Ref230017822 \r \h \* MERGEFORMAT [7]基于树莓派与MQTT协议实现了集协议转换、服务代理与数据管理于一体的智能网关，在数千次传输测试中数据丢失率为零。王猛 REF _Ref230017852 \r \h \* MERGEFORMAT [8]实现了同时兼容Zigbee与蓝牙协议的多协议网关，采用C/S架构经无线通信模块完成异构设备的集中远程控制与自动发现。
方纪磊 REF _Ref230017870 \r \h \* MERGEFORMAT [9]完成了支持边缘计算任务的物联网网关原型系统的设计与实现，验证了边缘侧任务调度与本地处理的技术可行性。王琦锋 REF _Ref230017883 \r \h \* MERGEFORMAT [10]以ESP32为核心节点，构建了基于MQTT与ESP‑NOW的智能家居监测与联动系统，采用“云—边—端”三层架构并借助Docker容器技术实现了多协议终端的灵活接入。
1.2.2 国外研究现状
国外在边缘计算与物联网网关领域起步较早，已形成若干成熟的技术流派。Desai等人 REF _Ref230017924 \r \h \* MERGEFORMAT [11]提出了语义网关即服务架构，通过在网关层引入语义抽象机制，将异构协议的数据映射为统一的资源描述框架，有效解决了设备间数据格式差异引发的互操作障碍。Perera等人 REF _Ref230017937 \r \h \* MERGEFORMAT [12]从“传感即服务”的视角出发，构建了面向智能城市的多协议物联网网关，验证了将底层传感能力封装为可调用服务的技术路径。Li等人 REF _Ref230017954 \r \h \* MERGEFORMAT [13]则从安全维度切入，提出了一种基于代码相似性分析的边缘网关漏洞自动化检测方法，为网关安全防护补充了新的技术视角。
Ray REF _Ref230017976 \r \h \* MERGEFORMAT [14]在其物联网架构综述中系统对比了集中式云处理与边缘处理的性能特征，明确了边缘计算在压缩上行带宽、降低传输时延、强化本地隐私保护方面具备结构性优势。Stojkovic等人 REF _Ref230017990 \r \h \* MERGEFORMAT [15]设计的智能家居网关采用了分层架构思想，在网关内部完成Zigbee与Wi‑Fi等协议的双向数据转换，同时引入校验确认与重传机制保障传输可靠性，实测丢包率低于1%，通信时延控制在115毫秒以内。
1.2.3 研究述评
综合国内外已有研究成果，可以把握两条演进主线：一是多协议适配技术正从硬编码的协议转换器向可扩展的语义抽象层演进；二是系统架构正从云端集中式向边端协同式迁移。前人在协议适配、数据融合和架构设计等方面奠定了扎实的工作基础。但若将视线投向真实的家庭部署环境，仍有几个方向值得进一步深化。其一，多数研究围绕特定协议组合开展适配，对动态设备接入与多协议并发场景下的调度策略探讨有限；其二，网关在长时间不间断运行中的稳定性、断网恢复后的数据补传完整性等工程化指标的系统性验证仍显薄弱；其三，现有方案中本地联动规则的配置灵活性不够理想，难以适应家庭用户多样化的场景需求。
针对上述缺口，本文从系统工程视角出发，设计并实现一套融合Wi‑Fi、BLE与MQTT的边缘智能网关，重点在协议适配模块的轻量化、统一数据模型的规范化定义、本地联动规则的灵活配置以及端到端性能的系统化验证等方面展开工作。
1.3 研究内容与技术路线
本文以智能家居场景中多协议设备的互联互通为核心问题，遵循“文献调研→需求分析→方案设计→硬件搭建→软件开发→集成测试→总结分析”的研究路径逐步推进。在文献调研与需求分析阶段，通过梳理国内外多协议网关与边缘计算领域的代表性成果，识别出协议异构、云端依赖过强、响应时延偏高等关键痛点，据此明确了边缘智能网关的功能边界与性能指标。

第2章 智能家居无线通信协议与关键技术分析
2.1 智能家居主流无线通信协议比较分析
智能家居场景中的无线通信协议呈现显著的技术分野，不同协议在传输速率、功耗特征、网络拓扑能力及安全性等方面各擅胜场。当前市场中占据主要份额的协议包括Wi-Fi、蓝牙低功耗（BLE）、Zigbee、Z-Wave、Thread以及LoRaWAN等，各自锚定差异化的应用场景。
Wi-Fi基于IEEE 802.11系列标准演进而来，当前家庭环境普遍使用的是802.11n（Wi-Fi 4）和802.11ac（Wi-Fi 5）两个版本。Wi-Fi工作在2.4GHz和5GHz双频段，物理层采用正交频分复用（OFDM）调制技术，通过多子载波并行传输来提升频谱效率。在2.4GHz频段，Wi-Fi将可用频谱划分为13个信道（国内标准），每个信道带宽20MHz，相邻信道之间存在频谱重叠，实际非重叠信道仅三个（信道1、6、11）。MAC层则采用带有冲突避免的载波侦听多路访问机制（CSMA/CA），节点在发送数据前先监听信道状态，若信道空闲则等待一个随机回退周期后启动发送，以此降低碰撞概率。Wi-Fi的峰值速率已经可达数百Mbps，使其天然适合承载视频监控、高清音频流等高带宽业务，但百毫安级别的活跃功耗也使其难以应用于电池供电的传感器节点。
BLE是蓝牙技术联盟在蓝牙4.0规范中引入的低功耗分支，后续版本（5.0/5.1/5.2）持续扩展了传输速率、通信距离和组网能力。BLE的物理层将2.4GHz ISM频段划分为40个信道（信道索引0–39），每个信道带宽2MHz，其中信道37、38、39被指定为广播信道，专门用于设备发现和连接建立，其余37个信道用于连接后的数据通信。链路层采用自适应跳频（Adaptive Frequency Hopping）策略：每次连接事件在37个数据信道之间伪随机切换，若某信道受到持续干扰则从跳频图谱中剔除，动态维持通信可靠性。BLE设备在休眠状态下的功耗可降至微安级别，一节CR2032纽扣电池足以支撑温湿度传感器持续工作数年。BLE 5.0引入的2Mbps高速模式和远距离编码（Coded PHY）进一步拓展了其适用范围，Mesh功能的加入则使其具备了多跳组网和覆盖扩展的能力。
Zigbee协议栈建立在IEEE 802.15.4物理层和MAC层之上，同样运行于2.4GHz频段，采用直接序列扩频（DSSS）技术将每个信道带宽限定为5MHz，共16个信道。Zigbee的网络层支持星型、树型和网状三种拓扑，网状拓扑中的路由器节点可自动构建多跳路径，单网络理论上限为65000个节点，扩展能力远超星型架构的Wi-Fi。Zigbee簇库（ZCL）定义了一组面向智能家居的标准化设备描述，涵盖照明、温控、安防等场景，厂商基于ZCL开发的设备在理论层面具备跨品牌互操作的可能。不过由于Zigbee不同版本（ZHA、ZLL、Zigbee 3.0）之间的兼容性裂痕，实际应用中仍需要网关充当协议翻译角色。
Z-Wave是Silicon Labs主导的家庭自动化专有协议，工作在Sub-1GHz频段（国内为868.4MHz）。相比于2.4GHz频段，Sub-1GHz电磁波具有更低的自由空间路径损耗和更优的墙体穿透能力，因此Z-Wave在复杂户型中的覆盖表现通常优于同功率的2.4GHz方案。其网状网络最多容纳232个节点，对于一般家庭而言足够使用，但较封闭的芯片供应生态一定程度上抑制了第三方终端的多样性。
LoRaWAN属于低功耗广域网（LPWAN）范畴，采用啁啾扩频调制技术实现超长距离通信，城市环境中2–5公里的覆盖半径使其更适合庭院灌溉、农田监测等户外场景，不属于当前室内智能家居的主流协议选择。

2.2 Wi-Fi协议栈结构与工作机制
IEEE 802.11协议栈的层次划分遵循OSI参考模型，但在数据链路层做了进一步细化：分为逻辑链路控制（LLC）子层和媒体访问控制（MAC）子层，物理层则分为物理层汇聚过程（PLCP）子层和物理介质依赖（PMD）子层。
Wi-Fi MAC层承担的核心职责包括信道接入控制、帧封装与解析、认证与关联、以及功率管理。在信道接入方面，标准定义了两种协调功能：分布式协调功能（DCF）和点协调功能（PCF）。DCF是基础接入模式，所有站点平等竞争信道使用权，依赖CSMA/CA算法避免碰撞。其工作流程为：发送站点开始检测物理载波和虚拟载波（基于网络分配矢量NAV），若信道在DIFS时长内持续空闲，则进入随机回退阶段；回退计数器在信道空闲期间递减，减至零时启动发送。接收方在成功接收后以短帧间间隔（SIFS）返回ACK确认帧，若发送方在ACK超时窗口内未收到确认，则推断碰撞发生，将竞争窗口翻倍后重新发起退避。这种指数退避策略使得多节点竞争下的信道利用率能够维持在合理水平。
Wi-Fi物理层在802.11n标准中引入了多输入多输出（MIMO）技术和信道绑定机制。MIMO利用多根天线同时发送和接收信号，通过空间流复用将数据吞吐量提升数倍，而无需增加频谱带宽。信道绑定则将两个20MHz信道合并为一个40MHz信道（或在802.11ac中绑定四个20MHz形成80MHz信道），成倍扩大符号传输速率。不过在实际家庭部署中，40MHz绑定在拥挤的2.4GHz频段往往弊大于利，因为这会侵占相邻Wi-Fi信道甚至BLE和Zigbee的频谱空间，反而加剧同频干扰。本系统的Wi-Fi终端节点（ESP32-S3）选用20MHz单信道模式，正是基于2.4GHz频段共存环境的这一现实考量。
Wi-Fi的关联与安全流程也是网关接入管理需要关注的技术细节。终端设备（STA）通过主动扫描或被动监听Beacon帧发现附近的接入点（AP），随后经历认证（Authentication）、关联（Association）两步握手过程才会进入数据通信状态。WPA2-PSK安全模式下，STA和AP通过四次握手（4-Way Handshake）协商出成对瞬态密钥（PTK），所有后续数据帧均以AES-CCMP算法加密。在本系统中，树莓派网关作为Wi-Fi接入点的角色由独立路由器承担，因此ESP32-S3节点与网关之间的通信属于同一局域网内的TCP Socket连接，网关侧无需处理Wi-Fi链路层的关联和密钥管理，简化了协议适配层的实现复杂度。
2.3 BLE协议栈结构与工作机制
BLE协议栈的架构可划分为控制器（Controller）、主机（Host）和应用（Application）三个层次，控制器与主机之间通过主机控制器接口（HCI）进行命令和事件的交互。
控制器层覆盖物理层和链路层。物理层如前所述，在40个2MHz信道中以1 Mbps（LE 1M）或2 Mbps（LE 2M）的符号速率进行GFSK调制。链路层定义了BLE通信的基本单元——连接事件（Connection Event）。在连接建立后，主设备（Master）和从设备（Slave）约定一个连接间隔（Connection Interval，取值范围7.5 ms至4 s），每个连接间隔内主设备在特定锚点时刻发起一次轮询，从设备在收到轮询后回复数据包，一个连接事件中可以交换若干对数据包。连接间隔是BLE功耗和延迟之间的核心调节参数：间隔越短，响应越快但功耗越高；间隔越长则相反。本系统中STM32F103终端节点的连接间隔配置为50 ms，该取值在保证250毫秒级联动响应需求的同时，将平均工作电流控制在毫安级别以下。
主机层由逻辑链路控制与适配协议（L2CAP）、属性协议（ATT）和通用属性规范（GATT）组成。L2CAP负责数据分片与重组，将上层协议数据单元适配到底层链路层的最大传输单元。GATT建立在ATT之上，将设备的数据组织为服务（Service）、特征（Characteristic）和描述符（Descriptor）的层次化结构。每个特征包含一个值和若干属性（如读权限、写权限、通知使能等），客户端可以通过ATT的读写和通知操作与特征值进行交互。
BLE的广播机制是实现低功耗设备发现和数据推送的关键技术。处于广播状态的从设备在三个广播信道上轮流发送广播包（Advertising Packet），广播间隔可在20 ms至10.24 s之间配置。广播包可携带最多31字节的厂商自定义数据，这对于传感器节点而言足够容纳温湿度、光照等少量传感数据的直接封装，使得网关在不建立GATT连接的情况下即可通过扫描广播包获取设备数据，从而实现真正的无连接感知。本系统的BLE适配器同时支持广播扫描模式和GATT连接模式：首次发现设备时通过广播包中的设备ID进行白名单匹配，匹配成功后根据需要建立GATT连接以获取更丰富的数据或下发控制指令。
2.4 MQTT协议特性与消息模型
MQTT（Message Queuing Telemetry Transport）是由IBM于1999年提出、后由OASIS标准化的轻量级应用层消息传输协议，当前广泛使用的版本包括3.1.1和5.0。MQTT的设计哲学源于对物联网场景中若干约束条件的高度抽象：设备处理能力有限、网络带宽窄且不可靠、消息交互以数据上报和指令下发为主体模式。
MQTT的核心架构围绕发布/订阅模型展开，与传统C/S模型的请求—响应不同，发布者和订阅者之间通过Broker（消息代理）解耦。发布者将消息发送至特定主题（Topic），Broker负责将消息路由给所有订阅了该主题的客户端，发布者无需知晓订阅者的身份和数量，订阅者也不必关心消息的来源。这种空间解耦机制大幅简化了多设备系统的消息路由逻辑。
MQTT定义了三种服务质量（QoS）等级以适应不同的可靠性需求。QoS 0（最多一次）：消息仅发送一次，不等待确认，可能丢失，适合传感器心跳这类允许偶发丢包的非关键数据。QoS 1（至少一次）：发送方持续重传直到收到PUBACK确认报文，保证消息至少送达一次（但可能重复），适合设备数据上报。QoS 2（恰好一次）：通过PUBREC到PUBREL到PUBCOMP四次交互确保消息不丢不重，开销最大，仅在对去重有严格要求的场景中使用。本系统采用QoS 1作为设备数据上报和控制指令的默认等级，心跳消息使用QoS 0以降低通信开销。
遗嘱消息（Last Will and Testament）是MQTT为应对设备异常离线而设计的特色机制。客户端在CONNECT报文中可以设定遗嘱主题和遗嘱消息内容，若客户端非正常断开连接（如网络中断、设备断电），Broker在检测到心跳超时后自动向遗嘱主题发布预设消息，通知其他订阅者该设备已离线。本系统利用遗嘱消息实现设备状态的自动更新：终端设备注册时将状态主题设置为遗嘱主题，遗嘱内容为offline，正常上线时发布online消息；当网关检测到设备遗嘱消息时，自动将设备状态标记为离线。
保留消息（Retained Message）是另一项实用特性：发布者可将某主题的最后一条消息标记为保留，Broker会存储该消息，并在新的订阅者加入时立即向其发送该保留消息。这一机制使得新上线的Web管理后台在订阅设备数据主题后能够立即获得各设备的最新状态快照，而无需等待下一轮数据上报周期。
MQTT主题采用UTF-8编码的字符串，以斜杠（/）作为层级分隔符，支持两种通配符用于批量订阅：加号（+）匹配单级主题段，井号（#）匹配其后所有层级。本系统采用了“home/区域/设备类型/设备ID/数据类型”五级主题结构，例如“ho--me/livingroom/temperature/sensor_01/data”表示客厅温度传感器的数据主题。基于通配符的订阅规则（如“home/+/+/+/data”订阅所有设备数据）使得系统能够以最小的订阅条目覆盖全局设备群。
2.5 边缘计算参考架构及其在本系统中的映射
边缘计算作为云计算向网络边缘的延伸，将计算、存储和网络资源下沉至靠近数据源的物理位置，以减少端到端延迟、缓解核心网带宽压力并增强数据隐私保护。欧洲电信标准化协会（ETSI）于2014年启动的移动边缘计算（后更名为多接入边缘计算MEC）标准化工作为边缘计算架构提供了系统性的参考框架。
ETSI MEC参考架构从逻辑上定义了移动边缘主机（ME Host）、移动边缘平台（ME Platform）、移动边缘应用（ME App）和移动边缘编排器（ME Orchestrator）等核心组件。移动边缘主机是承载边缘应用的物理或虚拟化基础设施，提供处理、存储和网络资源；移动边缘平台在NFVI（网络功能虚拟化基础设施）之上运行，为边缘应用提供无线网络信息、位置信息、带宽管理等服务能力；移动边缘应用以虚拟机或容器形式在平台之上运行，执行具体的业务逻辑；编排器则负责应用的全生命周期管理和资源调度。
将MEC架构映射到本系统的实际设计中，可以得到清晰的对应关系。树莓派4B作为移动边缘主机的物理承载，提供四核Cortex-A72处理器、2GB RAM和千兆以太网接口的计算与网络资源。EMQX消息中间件和Node-RED规则引擎构成了移动边缘平台的核心服务层：EMQX提供消息路由、主题管理和QoS保障能力，等价于MEC平台中的服务注册与服务发现；Node-RED则扮演边缘应用运行时的角色，承载各类自动化联动逻辑和数据处理流程。协议适配层（Wi-Fi适配器、BLE适配器）和设备管理器等Python应用模块作为具体的移动边缘应用实例，通过EMQX的发布/订阅接口与平台服务进行交互。
MEC架构强调的“本地业务分流与处理”原则在本系统中得到了直接体现。设备传感数据在网关侧经过协议解析、格式转换和规则匹配后，触发本地联动动作（如开启灯具），整个数据回路停留在家庭局域网内，无需穿越运营商的接入网和核心网。相比云端处理路径，该本地回路将控制响应时延从数百毫秒压缩至数十毫秒量级，断网场景下仍能维持联动功能的正常运行。
值得说明的是，ETSI MEC完整规范还涵盖了服务连续性、用户上下文迁移、合法监听等运营商级别的功能模块，这些模块在消费级家庭网关中并不具备部署的必要性。本系统对MEC架构的参照是选择性、裁剪性的：保留分层思想和边缘自治核心理念，舍弃面向移动网络的无缝切换、多租户编排等重量级机制，使架构复杂度与家庭网关的实际需求相匹配。
2.6 Wi-Fi与BLE在2.4GHz频段的共存机制分析
本系统同时运行Wi-Fi和BLE两种2.4GHz协议，频谱共存是影响通信可靠性的关键因素。从频谱布局角度分析，Wi-Fi信道宽度为20MHz（部分场景下可达40MHz），而BLE信道宽度仅2MHz。在典型的家庭Wi-Fi配置中，路由器通常占据信道1（中心频率2412MHz）、信道6（2437MHz）或信道11（2462MHz）。BLE的37个数据信道分布在2402MHz至2480MHz之间，与所有Wi-Fi信道均存在部分重叠。
当Wi-Fi和BLE信道在频域上重叠时，两种协议在物理上无法直接感知对方——协议不同，无法解码对方的帧前导码——同频干扰表现为接收端底噪抬升和信干噪比（SINR）恶化。Wi-Fi对BLE的干扰尤为突出：Wi-Fi发射功率通常为20dBm（100mW），而BLE典型发射功率为0dBm（1mW），两者的功率差使得在高占空比Wi-Fi传输期间，BLE接收端可能完全无法解调本应到达的蓝牙信号。
面对这一物理层现实，两类协议分别从不同层面设置了缓解策略。BLE的自适应跳频机制在连接建立后将信道质量评估结果反馈到跳频图谱中，标识出受干扰严重的信道并排除在跳频序列之外。即便某次连接事件使用的信道恰好被Wi-Fi占用，跳频机制也能确保下一次事件切换到干净信道，以概率性手段维持整体通信质量。
Wi-Fi侧的CSMA/CA机制则从时间维度上实现频谱共享。在网关所在环境中，ESP32-S3采集上报和环境控制指令的数据量较小（每包数十至数百字节），Wi-Fi信道占用率很低，大片时间窗口处于空闲状态。这为BLE在Wi-Fi静默期间完成数据交换留下了充足的时间裕量。实测表明，在低数据速率智能家居场景下，Wi-Fi和BLE的时域交织天然存在，无需专用协调硬件即可获得可接受的共存效果。
本系统还从工程实施角度增强了共存鲁棒性。树莓派4B的SoC集成了Wi-Fi和蓝牙双模无线子系统，内部已实现时域共存接口，能够协调两个射频模块的收发时序，避免同板同时收发导致的互扰。网关软件在BLE扫描和Wi-Fi Socket监听之间采取异步并发模型（Python asyncio），线程和协程调度器在操作系统层面分配CPU时间片，从时序上自然错开了两种协议的收发窗口。网关启动时自动扫描2.4GHz频段的信道占用分布，优先建议用户将Wi-Fi路由器信道调整到与BLE主要活动信道频差最大的位置——如Wi-Fi使用信道1时，BLE可将广播信道38（2426MHz）作为优先连接信道。这些措施共同作用，使系统在家庭电磁环境中能够实现Wi-Fi和BLE的稳定并行运行。
第3章 多协议边缘网关总体方案与开发平台
3.1 网关总体方案设计
基于第2章对Wi-Fi与BLE协议栈机制、MQTT消息模型以及边缘计算参考架构的分析，本章将这些技术要素整合为一套可工程化实施的总体方案。本系统采用四层分层架构，自下而上依次为设备接入层、协议适配层、消息路由与处理层、应用与联动管理层。各层之间通过标准化的JSON数据格式和层次化MQTT主题进行交互，以此实现功能解耦和模块间的独立演进。
图3.1系统整体分层架构图
如图3.1所示，设备接入层位于架构最底层，承担与各类智能家居终端设备的物理连接和原始数据收发职责。该层包含Wi-Fi接入模块、BLE接入模块以及预留的协议扩展接口。Wi-Fi接入模块以TCP Socket Server模式运行，监听指定端口等待ESP32-S3终端发起连接，接收传感器周期性上报的环境数据（温湿度、光照）。BLE接入模块基于Bleak异步库实现，通过扫描周边蓝牙广播包发现设备，按需建立GATT连接完成特征值读写和控制指令下发。两个模块各自独立运行，互不依赖，便于后续新增Zigbee协调器或其他协议接入硬件时以最小侵入方式扩展。
协议适配层位于设备接入层之上，承担异构协议数据的解析与转换职能。该层为每种支持的协议维护一个适配器实例：Wi-Fi适配器解析ESP32通过TCP Socket发送的原始文本帧，提取设备ID、传感数值和时间戳，进行完整性校验后交由协议转换器处理；BLE适配器通过GATT通知回调接收蓝牙终端推送的特征值数据，或直接解析广播包厂商数据段中携带的传感信息，转换为内部数据结构。协议转换器（Protocol Converter）是本层的核心组件，内部维护了设备类型到JSON字段的映射规则表——温度传感器的temp字段映射为data.temperature，光照传感器的lux或light_value字段映射为data.illuminance——同时将各种输入时序格式统一为Unix时间戳，将温度、湿度、光照单位分别标准化为摄氏度（celsius）、百分比（percent）和勒克斯（lux）。转换后的JSON消息交由MQTT适配器发布至EMQX消息代理。
消息路由与处理层是网关的数据中枢，负责消息的接收、缓存、路由和转发。该层的核心组件是EMQX消息代理，它接收来自协议适配层的JSON消息，按照发布/订阅模型将消息路由至所有匹配的订阅者——Node-RED规则引擎、Web管理后台的WebSocket推送通道，以及可选的云端桥接模块。消息路由器根据主题层级（home/区域/设备类型/设备ID/数据类型）实现自动分发，无需在代码中硬编码路由表。当EMQX与订阅者之间的连接因网络问题中断时，发布端的QoS 1确认机制和SQLite离线缓存机制协同保障数据不丢失。
应用与联动管理层面向用户和上层系统提供功能接口。Node-RED以可视化编排方式承载本地联动引擎，用户通过浏览器在画布上拖拽mqtt-in节点、function节点和mqtt-out节点即可搭建自动化规则，无需编写Python代码。Flask Web框架构建的管理后台提供设备注册与发现、实时状态监控、历史数据查询和联动规则配置等功能，前端通过MQTT over WebSocket实现设备状态的即时推送，用户操作延迟感知在数十毫秒级别。
图3.2 系统数据流架构图
图3.2展示了系统中一条完整数据链路的流动方向。上行方向：Wi-Fi终端（ESP32-S3+SHT30/BH1750）或BLE终端（STM32F103+HM-10）定时采集环境数据，经各自的无线协议发送至网关；网关的设备接入层接收原始数据帧，协议适配层完成解析与格式转换，生成统一的JSON消息；消息经消息路由层分发后，一部分推送给Node-RED规则引擎触发本地联动逻辑，一部分写入SQLite数据库用于状态回溯和离线缓存，另一部分通过MQTT Broker的WebSocket通道推送至浏览器端的Web管理后台。下行方向：用户在Web界面点击控制按钮，或Node-RED规则引擎根据阈值判定自动触发，控制指令以JSON格式发布至目标设备的control主题，经MQTT Broker路由至对应协议的适配器，最终转换为设备可识别的指令格式下发执行。整个数据链路在家庭局域网内闭环，脱离外网条件下上行采集和下行控制均不受影响。
3.2 硬件平台设计与实现
图3.4展示了本系统的硬件连接拓扑结构。系统以 Raspberry Pi 4B 作为边缘智能网关核心，通过千兆以太网接口与家庭无线路由器建立有线连接，同时利用板载 BCM43455 无线模块提供 Wi-Fi 2.4/5GHz 和 Bluetooth 5.0 BLE 双模无线接入能力。上位机 PC 通过局域网（LAN）接入同一路由器，实现对网关数据的远程监控。在感知层， ESP32-S3 节点通过 Wi-Fi 2.4GHz 与网关通信，挂载 DHT11 温湿度传感器（GPIO4）和有源蜂鸣器（GPIO5）； STM32F103ZET6 节点通过 HM-10 透传模组以 BLE 方式接入网关，挂载 GY-302(BH1750)光照传感器（I²C总线）和 RGB LED 指示灯（PE0~PE2）。网关侧预留 USB-A 接口和 GPIO 引脚，支持 ZigBee 协调器等扩展模块的接入。该拓扑实现了 Wi-Fi 与 BLE 异构协议的硬件层统一接入，为上层协议适配与数据融合提供了物理基础。

3.2.1 主控硬件平台选型
树莓派4B（Raspberry Pi 4 Model B）被选定为网关的核心主控单元，集中承担数据处理、协议转换、规则执行和资源管理等关键任务。选择该平台主要基于以下考量。
在计算性能与内存资源上，树莓派4B搭载Broadcom BCM2711四核Cortex-A72处理器，主频1.5GHz，配备2GB LPDDR4内存。这一配置足以支撑Python协议适配程序（多线程架构）、EMQX消息代理（MQTT连接管理和消息路由）、Node-RED规则引擎（Node.js运行时）以及Flask Web服务（WSGI服务器）的并发运行。实测中上述全部服务常驻运行时CPU平均负载约12%，内存占用约165MB，距离系统资源上限仍有充裕余量。
在接口扩展能力上，树莓派4B提供40针GPIO接口、两个USB 2.0接口、两个USB 3.0接口、千兆以太网接口以及板载双频Wi-Fi（802.11ac）和蓝牙5.0模块。USB 3.0接口可用于日后接入Zigbee协调器（如CC2531或EFR32MG21 USB Dongle）或高性能外置蓝牙适配器；GPIO接口可连接传感器扩展板或状态指示灯；千兆以太网接口为网关提供了稳定可靠的有线回程通道，避免了Wi-Fi回程可能引入的额外延迟抖动。
在软件生态层面，Raspberry Pi OS（基于Debian Linux发行版）为本系统提供了完备的基础运行环境。Python 3.9、Node.js 16、SQLite 3等核心依赖均通过官方APT仓库原生支持，安装部署流程简便。EMQX官方为ARM64架构提供了预编译的deb安装包，避免了从源码编译引入的时间和复杂度成本。社区活跃度方面，树莓派作为全球出货量最大的单板计算机之一，积累了丰富的开发文档和问题解决方案，大幅降低了系统集成过程中的调试门槛。
在成本效益上，树莓派4B（2GB版）板卡价格约300–400元人民币。考虑到它同时承担了网关的全部计算任务——替代了商业方案中独立的MQTT Broker硬件和联动主机——整体硬件成本控制在可接受范围内，符合消费级智能家居产品的成本敏感特征。
3.2.2 Wi-Fi接入模块设计
ESP32-S3是乐鑫科技面向AIoT场景推出的双核SoC，在本系统中承担Wi-Fi终端的环境数据采集与无线数据传输任务。该平台在无线连接性、计算能力和外设接口三个维度上满足系统需求。
无线连接方面，ESP32-S3集成2.4GHz Wi-Fi（802.11 b/g/n）和Bluetooth 5（LE）双模射频子系统，Wi-Fi最大物理层速率150Mbps。本系统中仅启用其Wi-Fi Station模式，ESP32-S3通过家用无线路由器接入局域网，以TCP Socket方式向网关服务器（树莓派4B，固定IP）的8888端口发起连接。信号覆盖方面，在120平方米典型户型中，ESP32-S3与路由器距离不超过15米且间隔不超过两面砖墙的条件下，链路质量稳定维持在-65dBm以上，满足智能家居终端通信的可靠性要求。
计算能力方面，ESP32-S3搭载Xtensa 32位LX7双核处理器，主频最高240MHz，内置512KB SRAM和384KB ROM，另可外挂最大16MB SPI Flash和8MB PSRAM。本系统的终端固件使用Arduino框架开发，传感器驱动层通过I2C总线以轮询方式读取SHT30温湿度传感器和BH1750光照传感器的数据，每10秒触发一次采集周期，传感器读写和JSON序列化的CPU占用率极低，单个核心利用率通常不超过15%。
外设接口方面，ESP32-S3提供SPI、I2C、I2S、UART、ADC、DAC等标准接口。实际接线中，SHT30的SCL和SDA引脚分别连接GPIO22和GPIO21（ESP32-S3默认I2C0总线），BH1750并接在同一I2C总线上（地址分别为0x44和0x23）。电源方面，ESP32-S3开发板通过Micro-USB供电（5V/1A），SHT30和BH1750由开发板3.3V输出引脚供电，无需额外电源模块。
3.2.3 BLE接入模块设计
BLE终端由STM32F103C8T6微控制器和HM-10蓝牙模块构成。STM32F103C8T6基于ARM Cortex-M3内核，主频72MHz，片内集成64KB Flash和20KB SRAM。HM-10模块以TI CC2541芯片为核心，固件实现了完整的BLE 4.0协议栈，通过UART接口对外提供AT指令集控制。
该组合方案在功耗控制上表现突出。STM32F103在正常运行模式下电流约数毫安，通过配置PWR_CR寄存器的SLEEPDEEP位进入STOP模式后可将电流降至10微安量级；HM-10模块的广播间隔设置为200ms，平均工作电流约数百微安。程序逻辑上，MCU上电初始化后读取SHT30传感器数据并通过UART以AT指令发送至HM-10，随后立即进入STOP模式并由RTC闹钟在10秒后唤醒，以此循环实现超低功耗的周期性数据上报。基于两节AA电池（约2500mAh容量）供电时，该终端理论续航可达6个月以上。
HM-10模块通过UART与STM32F103连接（PA9/TX和PA10/RX，波特率9600），GATT服务配置为Nordic UART Service（NUS）规范，TX特征（UUID: 6E400002-B5A3-F393-E0A9-E50E24DCCA9E）承载设备到网关的数据推送，RX特征（UUID: 6E400003-B5A3-F393-E0A9-E50E24DCCA9E）承载网关到设备的指令下发。设备首次上电时自动进入广播状态，在三个BLE广播信道上以200ms间隔轮发广播包，广告数据段中携带设备ID和当前传感器读数的压缩编码，使网关在不建立GATT连接的情况下即可通过扫描获取数据。
3.3 软件平台搭建与运行环境配置
3.3.1 操作系统选择与配置
网关软件运行于Raspberry Pi OS（64位，基于Debian Bullseye发行版）。系统安装使用Raspberry Pi Imager工具将官方镜像写入32GB以上容量的microSD卡，首次启动后通过raspi-config工具完成以下基础配置：启用SSH远程访问以便后续维护（Interfacing Options → SSH → Enable），通过raspi-config或/etc/dhcpcd.conf为eth0接口配置静态IP地址（本系统使用192.168.1.100），设置主机名为smart-gateway以区别于局域网内其他设备，将时区设定为Asia/Shanghai以确保日志时间戳与本地时间一致，最后执行raspi-config中的Expand Filesystem操作将文件系统扩展至SD卡全部可用容量。
安全性方面，安装完成后立即修改默认pi用户的密码；创建专用服务账户gateway-svc并通过systemd服务单元的User/Group指令限定EMQX、Node-RED和Python协议适配程序的运行权限，避免以root身份运行服务进程。防火墙配置（ufw）仅开放22端口（SSH，内网限定）、1883端口（MQTT，本地回环绑定）、8083端口（MQTT over WebSocket）、5000端口（Flask Web）和1880端口（Node-RED编辑器），其余端口默认拒绝。
3.3.2 EMQX消息中间件部署
EMQX 5.0作为本系统的消息中枢，负责全部MQTT消息的发布、订阅、路由和持久化。安装通过EMQX官方APT仓库执行，ARM64架构的预编译包保证了安装流程的简洁性。安装完成后对/etc/emqx/emqx.conf进行以下针对性调整。
监听器配置方面，创建两个独立的监听器实例：TCP监听器限定绑定地址为127.0.0.1:1883，仅允许本机运行的协议适配程序和Node-RED内部连接；WebSocket监听器绑定地址为0.0.0.0:8083，允许局域网内浏览器上的Web管理前台通过MQTT.js库直接连接获取实时数据推送。两者互不混淆，外部网络无法直接访问TCP MQTT端口，降低了端口扫描和未授权连接的风险。
资源参数调整方面，鉴于树莓派4B的2GB内存并非全部可用于EMQX，将消息队列的最大长度（max_mqueue_len）设置为1000，将会话的最大数量（max_session_count）限制为50。消息持久化功能关闭，由本系统的SQLite离线缓存模块承担断网期间的数据暂存职责，避免EMQX自身的磁盘持久化与SQLite产生双重IO负载。
ACL（访问控制列表）配置方面，建立两条核心规则：允许内部客户端（客户端ID以gateway_或nodered_为前缀）对全部主题拥有发布和订阅权限；允许Web客户端（客户端ID以web_为前缀）仅对home/#主题拥有订阅权限，仅对home/+/+/+/control主题拥有发布权限（即Web界面只能查看所有设备数据，只能下发控制指令，不能篡改data和status主题）。认证方面当前采用简单的username/password方式，后续可升级为JWT Token或X.509证书认证。
3.3.3 Node-RED规则引擎配置
Node-RED通过npm全局安装后配置为systemd自启动服务。启动后在浏览器中访问 http://192.168.1.100:1880进入可视化编辑界面。本系统预置了两个典型联动场景的流程模板。
光照自动控灯场景的流程结构为：mqtt-in节点订阅“home/+/light_sensor/+/data”主题（使用+通配符覆盖所有区域和设备），QoS设置为1，输出类型为解析后的JSON对象。function节点获取msg.payload.data.illuminance字段值并与预设阈值（默认100 lux）比较，低于阈值时构造开灯指令消息（含action字段和brightness字段）并通过return将消息传递给下一节点。mqtt-out节点动态设置主题为“home/”+msg.payload.location+“/light/lamp_001/control”，QoS 1，保留消息选项开启以确保新订阅者能获取最新灯具状态。
温湿度异常报警场景的流程类似：mqtt-in订阅“home/+/temperature/+/data”，function节点判断温度值是否超过35°C或湿度值是否超过80%，超限时将报警消息（含告警类型、越限数据和触发时间）传递至mqtt-out发布到“home/alert”主题。Web管理后台订阅“home/alert”主题后通过浏览器Notification API向用户桌面推送报警通知。
3.3.4 协议适配程序运行环境
网关的核心业务逻辑——协议适配、数据转换、离线缓存、Web后台——全部基于Python 3.9开发，通过pip安装依赖库。依赖清单（requirements.txt）包含Flask（Web框架）、flask-socketio（WebSocket推送）、paho-mqtt（MQTT客户端）、bleak（跨平台BLE异步库）、pyserial（串口通信，预留）和python-dotenv（环境变量管理）。
程序架构采用多线程模型。主线程（MainThread）负责加载配置文件、初始化各子模块并启动系统监控日志。Wi-Fi适配线程以阻塞模式运行TCP Socket Server，在accept()返回新连接后以daemon线程处理该设备的数据收发，主线程不阻塞。BLE适配线程以asyncio事件循环运行，在单独线程中启动BleakScanner扫描周边蓝牙广播，设备发现和GATT连接操作在asyncio事件循环内异步完成。MQTT发布线程持有queue.Queue实例，各协议适配器将待发布消息入队，发布线程循环从队列取出消息并调用paho.mqtt.client.publish()完成发布。
Web管理后台基于Flask应用工厂模式组织代码，项目目录结构按功能划分为三个蓝图（Blueprint）：设备管理蓝图（device_bp）处理设备注册、发现、状态查询和控制指令下发等接口；认证蓝图（auth_bp）负责用户登录会话管理；系统蓝图（system_bp）提供系统配置修改和运行日志查看接口。前后端之间的实时数据推送不依赖HTTP轮询，而是利用MQTT over WebSocket机制：前端页面加载时通过MQTT.js库连接EMQX的WebSocket端口并订阅相关主题，设备状态更新和传感器数据变化直接由MQTT推送至浏览器，用户无需手动刷新页面。

4.2.2 MQTT主题命名规范
本系统的MQTT主题遵循层次化命名原则，采用四级结构： smarthome/v1/&lt;消息类型&gt;/&lt;设备类型&gt;/&lt;设备ID&gt; 。其中第一级smarthome为命名空间，第二级v1为协议版本号，第三级按消息流向分为telemetry（上行遥测）、command（下行命令）和status（状态事件），第四级和第五级分别对应设备类型和设备ID。

4.3.1 Wi-Fi适配模块实现
Wi-Fi适配模块（wifi_receiver.py）同时向外暴露两种接入通道，终端固件可任选其一。HTTP通道基于Flask框架构建，在8080端口提供 POST /api/v1/telemetry 端点，终端以HTTP POST方式提交JSON格式的传感数据。TCP通道基于Python asyncio的StreamReader/StreamWriter接口构建，在9000端口监听原始字节流，终端每发送一行以换行符结尾的JSON文本，服务端即读取一行、解析、转换并回调on_message。
两种通道的数据最终汇入同一处理路径：原始JSON经normalize_wifi()函数完成字段映射（短键名t/h/l/lux分别映射为temperature/humidity/light/illuminance）、单位标准化和时间戳补全，生成统一消息后触发on_message回调。TCP通道额外维护一个device_id到StreamWriter的映射字典，使网关的on_command下行分发器能够按device_id定位到对应TCP连接，将控制指令写回终端。

4.3.2 BLE适配模块实现
BLE适配模块（ble_receiver.py）基于跨平台异步BLE库Bleak实现，以asyncio事件循环驱动扫描与连接逻辑。模块启动后进入周期扫描循环（默认5秒间隔），扫描结果按设备名前缀（如SHMPEG-、BT05、HMSoft）进行白名单过滤，匹配成功的设备由独立协程建立GATT连接。
连接目标为HM-10蓝牙模块（TI CC2541芯片），其GATT服务遵循Nordic UART Service规范，Notify特征UUID为0000ffe1-0000-1000-8000-00805f9b34fb。HM-10固件的单次Notify数据上限约20字节，长JSON帧可能被拆分为多个分片送达。适配器内部为每个device_id维护一个字节缓冲，将接收到的分片按\n分隔符重组成完整数据帧后再调用normalize_ble()转换为统一消息。

4.4 协议转换与消息路由模块设计实现
协议转换与消息路由模块是网关的核心枢纽，负责将Wi-Fi和BLE适配器生成的统一JSON消息发布到正确的MQTT主题上。协议转换由data_converter.py中的normalize_wifi()和normalize_ble()两个入口函数完成，消息路由由mqtt_publisher.py中的MqttPublisher类接管。
Wi-Fi数据的标准化流程为：接收到的原始JSON中可能包含短键名（t、h、l、b）或长键名（temperature、humidity、light、battery），normalize_wifi()通过alias_map字典将短键名统一转换为长键名，保留未识别字段以支持未来扩展，从ts或timestamp字段提取Unix时间戳，将device_id、device_type（固定为wifi）、transport（http或tcp）、payload和status五个参数传入build_unified_message()构造最终消息。
BLE数据处理路径略有不同：normalize_ble()接收原始字节数组而非JSON字典，需要先尝试按UTF-8解码为文本，若解码失败则按十六进制编码转储。解码成功的文本按JSON解析后提取可识别的传感字段（temperature、humidity、light、battery、co2、pm25等），未识别的键原样保留。
消息路由的核心逻辑封装在MqttPublisher.publish_unified()方法中。该方法从统一消息中取出device_type和device_id字段，调用telemetry_topic()拼接完整主题路径，再调用publish()将JSON字符串发布到EMQX。publish()方法在发布前会检查连接状态：若已连接则直接发布；若未连接且本地缓存已启用，则将消息写入cache队列，等待后台重发线程在网络恢复后逐一回传。

4.5 本地自治联动与离线补传机制实现
4.5.1 Node-RED联动规则编排
本地自治联动功能通过Node-RED的可视化流编辑器实现。本地联动规则以Node-RED的可视化流程（flow）形式编排，流程定义存储在flows.json文件中并通过EMQX与网关Python模块交互。本系统预置了两条核心跨协议联动规则。
光照联动规则的数据流为：mqtt-in节点订阅 smarthome/v1/telemetry/+/+ 主题接收全部设备上行数据，function节点（cache-peer-id）将最近一次见到的各类型device_id缓存至flow上下文；switch节点按device_type分流，BLE数据经light-low规则判断payload.light值是否低于50 lux，低于阈值时从flow上下文取出最近活跃的Wi-Fi设备ID，构造包含led字段和src_seq追踪字段的JSON命令，通过mqtt-out节点发布到 smarthome/v1/command/wifi/&lt;id&gt; 主题。
温度联动规则类似但方向相反：Wi-Fi数据经temp-high规则判断payload.temperature是否超过28°C，超限时取出最近活跃的BLE设备ID，构造蜂鸣命令（beep:3）下发至BLE终端。Rule中的src_seq字段传递了触发设备的序列号，测试阶段可通过匹配上行与下行消息中的seq值精确计算端到端联动延迟。
4.5.2 SQLite离线缓存机制
为确保网络中断场景下的数据不丢失，本系统实现了基于SQLite的离线缓存机制。离线缓存模块（cache.py）基于Python标准库sqlite3实现，不依赖任何外部数据库驱动。数据库文件以WAL（Write-Ahead Logging）模式打开，避免了读写操作之间的锁冲突。outbox表结构仅含五个字段：自增主键id、topic、payload、qos和created_at时间戳。
消息写入通过push()方法完成：插入新行后检查总行数是否超出max_rows上限（默认100000），超出则按FIFO策略删除最早的行。消息重发由后台线程按固定周期（默认10秒）执行：peek()取出前100条待发消息，逐条调用paho-mqtt的publish发送，发送成功的行ID收集到列表，批量调用delete()清理。整个流程线程安全——所有公共方法均使用threading.Lock保护，且每次调用创建短连接，规避了sqlite3跨线程使用同一连接的限制。
代码清单4.6 SQLite离线缓存核心方法
def push(self, topic, payload, qos=1):
 with self._lock, self._connect() as conn:
 cur = conn.execute(
 "INSERT INTO outbox (topic, payload, qos) VALUES (?,?,?)",
 (topic, payload, qos))
 count = conn.execute("SELECT COUNT(*) FROM outbox").fetchone()[0]
 if count &gt; self._max_rows:
 overflow = count - self._max_rows
 conn.execute(
 "DELETE FROM outbox WHERE id IN "
 "(SELECT id FROM outbox ORDER BY id ASC LIMIT ?)", (overflow,))
def peek(self, limit=100):
 with self._lock, self._connect() as conn:
 return [tuple(r) for r in conn.execute(
 "SELECT id, topic, payload, qos FROM outbox ORDER BY id ASC LIMIT ?",
 (limit,)).fetchall()]

4.6 设备管理与Web管理台实现
Web管理台基于Flask框架构建，与网关主程序共享同一进程空间。管理台的功能范围涵盖用户认证、设备节点管理和实时状态展示三个方面。
认证系统基于Flask Session实现，用户密码使用werkzeug.security的generate_password_hash()以pbkdf2:sha256算法哈希存储。登录接口POST /api/v1/admin/login 在用户名或密码错误时返回401，连续失败5次后账户锁定15分钟（锁定期间返回423状态码及剩余等待秒数）。首次启动时若admin_users表为空，系统自动创建admin/admin引导账户。角色分为admin和user两级，通过admin_required装饰器保护用户创建/修改/删除等敏感接口。
节点管理通过admin_nodes表和node_presence表协同工作。admin_nodes表存储设备的静态信息：统一标识符（unified_id）、设备类型（device_type）、原生设备ID（native_device_id）、显示名称（display_name）和传输协议类型（transport）。node_presence表记录设备的最后活动时间，网关主控流程中每收到一条上行数据即调用note_device_seen()更新该设备的last_seen字段。Web管理台的节点列表接口按admin_online_grace_sec配置的宽限期（默认120秒）判定设备在线状态——last_seen在宽限期内为online，超出为offline。

5.2.2 功能测试结果分析
设备接入测试中，ESP32上电后3–8秒内通过TCP连接到网关的9000端口并完成注册帧交互，随后进入以5秒为周期的定期上报模式。BLE终端上电后约1–3秒内被网关扫描发现，设备名匹配白名单（前缀SHMPEG-或BT05）后建立GATT连接，平均建连耗时2.1秒。

跨协议联动测试以“BLE光照传感器检测到环境变暗→触发Wi-Fi灯具开启”为验证链路。测试人员用手掌完全遮挡BLE节点的BH1750传感器后，Node-RED规则在约85毫秒内完成阈值判断和指令构造（实测mqtt-in节点接收到data消息到mqtt-out节点发布command消息的时间差），ESP32终端在收到TCP指令后约45毫秒内驱动LED变为黄色。联动全链路的行为符合flows.json中预置规则的定义。

5.3 性能测试与结果分析
5.3.1 MQTT基准性能
在正式测量系统性能之前，先对EMQX消息代理自身进行基准测试，作为后续端到端测量的参考基线。测试工具向本地回环EMQX（127.0.0.1:1883）以5毫秒间隔发布1000条QoS 1消息，每条消息的payload中嵌入纳秒级send_ns时间戳，订阅端计算接收时刻与发送时刻之差得出消息传输时延。
基准测试结果：1000条消息全部送达，丢包率0%；回环传输时延最小0.42毫秒、平均0.78毫秒、P95为1.35毫秒、最大4.90毫秒；吞吐率约825条/秒。该结果表明EMQX在树莓派平台上运行高效，消息代理本身引入的延迟在亚毫秒级，不会成为系统端到端延迟的瓶颈。
5.3.2 端到端传输时延
端到端时延定义为从终端传感器读取数据并序列化完毕的时刻，到网关MQTT发布器成功将消息发布至EMQX的时刻之间的时间跨度。测试使用cross_device_perf_subscribe脚本订阅telemetry主题，在终端payload中以seq字段标记包序号、以send_ns字段记录纳秒时间戳（需ESP32通过NTP与网关同步时钟），订阅端逐包计算recv_ns与send_ns之差。

结 论
本研究针对智能家居场景中Wi-Fi与BLE协议设备难以跨协议互通、传统云端架构存在延迟与断网不可用等问题，设计并实现了一款面向家庭环境的多协议边缘智能网关。工作内容覆盖协议特性分析、总体方案设计、硬件平台搭建、软件模块开发与系统测试验证的全流程。
一、工作总结
硬件与系统实现方面 ，构建了以树莓派4B（2GB）为网关主控、ESP32-S3为Wi-Fi终端节点、STM32F103配合HM-10模块为BLE终端节点的异构硬件平台。网关侧部署了Python协议适配程序、EMQX消息代理、Node-RED规则引擎、Flask Web管理后台和SQLite离线缓存模块，形成了完整的边缘计算软件栈，全部组件在Raspberry Pi OS上稳定运行。
协议适配与数据互通方面 ，实现了Wi-Fi（HTTP与TCP双模式）和BLE（广播扫描与GATT连接双模式）两类协议的终端接入，通过定义统一的JSON消息格式和层次化MQTT主题规范（smarthome/v1/telemetry/&lt;device_type&gt;/&lt;device_id&gt;），将异构协议数据归并为标准化消息流，打通了Wi-Fi传感器与BLE传感器之间经由网关中转的跨协议数据通道。
本地联动与边缘自治方面 ，利用Node-RED可视化编排工具构建了跨协议自动化规则——以“BLE光照传感器检测到环境变暗后触发Wi-Fi灯具开启”为典型场景，实测联动全链路响应时延约135毫秒，远低于500毫秒的设计阈值。断网场景下，Node-RED规则引擎在局域网内正常执行、SQLite缓存模块完整记录待补传数据、网络恢复后缓存消息100%成功回传，验证了边缘自治架构脱离云端后的独立运行能力。
系统测试与性能验证方面 ，功能测试七项用例全部通过。性能测试得出Wi-Fi路径端到端时延均值43.5毫秒、BLE路径均值76.8毫秒；受实验硬件数量限制，并发场景以MQTT合成遥测数据模拟逻辑终端，10设备并发时系统运行平稳、时延升至95.2毫秒仍处可接受范围；丢包率Wi-Fi路径0.06%、BLE路径0.17%，数据准确率超过99.8%。稳定性测试中系统7×24小时无故障运行，内存占用在2GB总容量中仅占约180MB，断网恢复补传成功率100%。五项设计指标全部达标且显著优于阈值。
二、不足分析
受实验条件制约，本研究存在以下局限。硬件方面，实体设备仅包含一台Wi-Fi终端和一台BLE终端，多设备并发场景采用MQTT合成遥测模拟，无法完全反映真实射频环境中多终端同时发包时的同频干扰和信道竞争状况，测试结论的外推范围有限。协议覆盖方面，当前仅适配Wi-Fi和BLE两种协议，课题任务书中规划的Zigbee扩展接口尚未激活，Thread和Matter等新兴协议亦未纳入。安全机制方面，EMQX当前采用用户名/密码的基础认证，设备与网关之间的MQTT通信未启用TLS加密，Web管理后台的Flask Session在跨网络部署时存在会话劫持风险，整体安全防护水平处于原型验证阶段。Web管理台的前端界面较为简单，仅完成桌面端适配，移动端浏览器上布局和交互体验有待改进。
三、后续工作展望
基于上述不足，后续可从以下方面推进。协议扩展方面，通过USB接口接入Zigbee协调器并在Python协议适配层中新增对应适配器实例，实现三类协议的统一接入；长远来看，Matter协议作为智能家居互联互通标准值得重点关注，其IP化设计思想与本系统的MQTT消息总线架构在数据抽象层面具有可类比性。智能化提升方面，可在树莓派上部署轻量级TinyML推理引擎，利用历史传感数据训练简单的用户行为预测模型，将联动逻辑从固定阈值判断升级为数据驱动的自适应决策。安全加固方面，为EMQX配置TLS/SSL证书实现加密传输，引入JWT或X.509证书进行设备身份认证，在admin_routes模块中增加CSRF防护和会话超时机制。工程化改进方面，将Python协议适配器、Node-RED流程和EMQX配置统一打包为Docker Compose编排文件，实现一键部署和版本化管理。
